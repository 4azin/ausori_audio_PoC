# AI 파이프라인 비용 절감 분석

> 작성일: 2026-04-16
> 현재 비용: ~$1.20/건 (Docker 환경 기준)

---

## 1. 현재 비용 구조

### 파이프라인 흐름

```
영상 입력
  → [Global] 프레임 추출 (1fps, max 180) → Gemini 호출 1회
  → [Foley] scene별 프레임 추출 (2fps, max 30) → Gemini 호출 N회
  → [Non-foley] scene별 프레임 추출 (2fps, max 30) → Gemini 호출 N회
```

### 이미지 전송 방식

- `types.Part.from_bytes(data=data, mime_type="image/jpeg")` — 인라인 바이트 전송
- ffmpeg으로 프레임 추출 → JPEG 768px 리사이즈 → 바이트로 읽어서 전송

### 토큰 소비 (10 scene 기준, ~80초 영상)

| 단계 | API 호출 수 | 프레임 수 | 이미지 토큰 (258 tok/장) |
|------|------------|-----------|------------------------|
| Global | 1회 | ~80장 | ~20,640 |
| Foley | ~10회 | scene당 ~30장 (총 ~300장) | ~77,400 |
| Non-foley | ~10회 | scene당 ~30장 (총 ~300장) | ~77,400 |
| **합계** | **~21회** | **~680장** | **~175,440** |

- 여기에 프롬프트 텍스트 토큰이 추가됨
- 모델: `gemini-3-flash-preview` 기준 input $0.30/1M, output $2.50/1M

## 2. 비용 절감 방안

### 방안 1: Gemini File API로 영상 직접 업로드 (권장 — 최우선)

프레임 추출 없이 영상 파일 자체를 Gemini에 업로드.

**원리**
- Gemini 비디오 토큰: 1초 ≈ 263 tokens
- 80초 영상 → ~21,040 tokens
- vs 프레임 180장 인라인 → ~46,440 tokens
- Global 단계만으로 ~50% 이미지 토큰 절감

**구현 방향**
```python
# 현재
frame_parts = [Part.from_bytes(data=data, mime_type="image/jpeg") for ...]
contents = [prompt_text] + frame_parts

# 변경
video_file = client.files.upload(file=video_path)
contents = [prompt_text, video_file]
```

**장점**
- ffmpeg 프레임 추출 전처리 제거 → 파이프라인 속도 향상
- 토큰 효율 대폭 개선
- 영상의 시간 연속성 정보를 Gemini가 직접 활용 (프레임 시퀀스보다 풍부)

**단점/주의**
- 파일 업로드 시간 추가 (네트워크 의존)
- 업로드 파일 크기 제한 확인 필요
- scene별 로컬 분석 시 trim된 영상을 업로드해야 함

---

### 방안 2: Context Caching (Foley + Non-foley 영상 공유)

같은 scene에 대해 Foley와 Non-foley가 동일한 영상/프레임을 각각 보내는 중복 제거.

**원리**
- Gemini Context Caching: 캐시된 토큰은 $0.075/1M (일반 input $0.30/1M 대비 75% 할인)
- scene 영상을 한 번 캐시 → Foley/Non-foley 두 호출에서 재사용

**구현 방향**
```python
# scene 영상 업로드 후 캐시 생성
cache = client.caches.create(
    model=MODEL,
    contents=[video_file],
    config=types.CreateCachedContentConfig(
        display_name=f"scene_{scene_id}",
        ttl="300s",
    ),
)

# Foley 호출 (캐시 사용)
response = client.models.generate_content(
    model=MODEL,
    contents=[foley_prompt],
    config=types.GenerateContentConfig(cached_content=cache.name),
)

# Non-foley 호출 (같은 캐시 재사용)
response = client.models.generate_content(
    model=MODEL,
    contents=[non_foley_prompt],
    config=types.GenerateContentConfig(cached_content=cache.name),
)
```

**장점**
- 로컬 분석 이미지 토큰 ~154K 중 절반이 캐시 히트
- File API와 조합 시 극대화

**단점/주의**
- 캐시 최소 토큰 수 요구사항 확인 필요 (Gemini 캐시는 최소 32K 토큰)
- TTL 관리 필요
- scene이 짧을 경우 최소 토큰 미달 가능

---

### 방안 3: Foley + Non-foley 단일 호출 병합

scene당 2회 호출 → 1회로 통합.

**원리**
- 프롬프트에 Foley/Non-foley 분석을 동시 요청
- JSON 출력에 `foley_events` + `non_foley_tracks`를 함께 포함

**구현 방향**
- 통합 프롬프트 작성 (Foley + Non-foley 규칙 병합)
- 출력 스키마를 `{ "foley_events": [...], "non_foley_tracks": [...] }` 로 변경
- `pipeline.py`에서 결과 파싱 로직 수정

**장점**
- API 호출 수 ~21회 → ~11회 (절반)
- 영상 토큰 중복 전송 완전 제거
- 네트워크 라운드트립 절감

**단점/주의**
- 프롬프트가 복잡해져서 출력 품질 저하 가능성
- 출력 JSON이 커져서 output 토큰 증가
- Foley/Non-foley 독립 튜닝이 어려워짐
- A/B 테스트로 품질 검증 필요

---

### 방안 4: 프레임 수 최적화 (File API 미적용 시 대안)

분석 단계별 특성에 맞게 프레임 수를 조정.

| 단계 | 현재 | 제안 | 이미지 토큰 절감 |
|------|------|------|----------------|
| Global | 1fps, max 180 | 0.5fps, max 80 | ~55% |
| Foley | 2fps, max 30 | 1fps, max 20 | ~33% |
| Non-foley | 2fps, max 30 | 0.5fps, max 10 | ~66% |

**근거**
- Global: 장면 분할은 전체 흐름만 파악하면 됨 → 프레임 밀도 낮아도 무방
- Foley: 행위 기반이라 프레임 밀도가 품질에 직결 → 보수적 조정
- Non-foley: 분위기/배경 분석이라 세밀한 프레임 불필요 → 공격적 절감

## 4. 적용 우선순위

```
1순위: File API 전환
  → 가장 쉽고 효과 큼. 코드 변경 범위 작음.
  → analyze_global.py, analyze_local_foley.py, analyze_local_non_foley.py 수정

2순위: Context Caching
  → File API 적용 후 추가 적용. scene 영상 캐시 공유.
  → pipeline.py에서 캐시 생명주기 관리 추가

3순위: 호출 병합 (Foley + Non-foley)
  → 품질 검증 후 적용. 프롬프트 재설계 필요.
  → 새 통합 프롬프트 + pipeline.py 결과 파싱 수정

4순위: 프레임 수 최적화
  → File API와 병행 불가 (대안 관계). File API 못 쓸 경우 적용.
```
