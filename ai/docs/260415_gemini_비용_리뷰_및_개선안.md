# Gemini 호출 비용 리뷰 및 개선안 (2026-04-15)

AI 영상 분석 파이프라인(`ai/pipeline.py`) 의 현재 Gemini 호출 구조를 비용 관점에서 점검한 결과를 팀 공유용으로 정리한다.

---

## TL;DR

- "Background search(=Google Search grounding)" 는 **우리 코드엔 없음** (tools 미지정) → 이 경로의 과금 걱정은 없다.
- 진짜 리스크는 **인라인(base64) 프레임 전송 경로** 쪽이다.
- 특히 **같은 scene 의 프레임을 foley·non-foley 가 각자 추출해서 따로 전송** 중이라, 이미지 토큰이 거의 2배로 나간다. 여기가 1순위 절감 포인트.

---

## 1. 비용이 비싸게 나올 법한 지점

### 1.1 같은 프레임을 scene 당 2번 전송 (foley + non-foley)
`analyze_local_foley.analyze_scene` 과 `analyze_local_non_foley.analyze_scene` 이 각자 독립적으로 `trim_video → extract_frames → load_frames_as_parts` 를 수행한다. 결과: scene 수 × 2 만큼 동일 프레임을 Gemini 에 중복 전송. 이미지 토큰 비용이 그대로 2배.

### 1.2 프레임이 전부 inline base64
`types.Part.from_bytes(data=..., mime_type="image/jpeg")` 는 요청 바디에 base64 로 직렬화되어 들어간다. base64 자체가 추가 과금은 아니지만:
- 요청 크기가 커져 타임아웃/5xx 재시도 빈도가 올라가고, 재시도마다 비용이 발생한다.
- `cachedContent` (prompt caching) 혜택을 못 받는다. 매 호출 "프롬프트(수 KB) + 이미지(수 MB)" 풀세트를 처음부터 다시 보낸다.
- Files API 로 비디오를 한 번 업로드해 URI 로 참조하면 **이미지 토큰 대신 비디오 토큰(초당 고정)** 으로 과금되는데, 이 경로보다 보통 더 비싸다.

### 1.3 긴 시스템 프롬프트 × scene 수 반복
- `foley_analyzer` ≈ 5KB, `non_foley_analyzer` ≈ 8KB (taxonomy 포함).
- scene N 개면 foley/non-foley 각각 N 회 프롬프트 전문 재전송.
- 실제 호출마다 달라지는 건 scene 메타데이터뿐. 공통 본문은 고정인데 캐싱 미사용.

### 1.4 Global 프레임 180장
`analyze_global` 기본 `max_frames=180`. Gemini 이미지 토큰 환산 규칙상 장당 258~수백 토큰, 180장이면 global 한 번에 수만~10만 토큰이 쉽게 들어간다. 원본 비율이 넓어 "high-res tiled" 조건에 걸리면 장당 토큰이 추가로 상승한다.

### 1.5 실패 재시도 비용
`llm_client._call_with_retry` 는 503/429/5xx 에 최대 5회, 2→4→8→16→32초 지수 백오프로 붙는다. Gemini 가 "요청 받은 뒤 5xx" 로 떨어지는 케이스에선 부분 과금이 발생할 수 있어, 반복 실패 구간 전체가 돈이 될 수 있다. 특히 고단가 모델(`pro`) 에서 위험.

### 1.6 해상도
현재 `scale=768:-2`. 대부분 표준 tile 이지만 원본이 16:9 와이드면 tiled 로 승격될 수 있다. 해상도 한 단계 낮추면 장당 이미지 토큰이 떨어질 여지가 있다.

## 2. 개선안 (효과 큰 순서)

### A. scene 프레임을 foley·non-foley 가 공유 — **1순위**
`pipeline.py` 레벨에서 scene 별 프레임을 한 번만 추출해 두고, foley/non-foley 호출에 동일 parts 를 주입한다. 이미지 토큰 비용 **최대 절반**.

```python
# 개념
for scene in scenes:
    parts = extract_scene_parts(video, scene, fps, max_frames)
    foley_result = foley.analyze_scene_with(parts, scene, ...)
    non_foley_result = non_foley.analyze_scene_with(parts, scene, ...)
```

현재 analyzer 의 `analyze_scene(...)` 시그니처를 `parts` 를 받도록 리팩터 필요.

### B. Prompt caching (`cachedContent`) — scene 수가 많을수록 이득
시스템 프롬프트 + taxonomy 를 `client.caches.create(...)` 로 캐시한 뒤, scene 호출은 `cachedContent=...` 만 참조한다. 캐시 가격은 보통 일반 입력 대비 1/4 수준 (PRICING 테이블의 `cached` 필드 참조). scene 10개 이상이면 체감 큼.

### C. Global 프레임 수 절감 — 무해한 튜닝
`max_frames=180 → 60~90` 으로 낮추고, scene 분할 품질이 떨어지는지 A/B 확인. 떨어지지 않으면 그대로 고정. global 한 번 호출 이미지 토큰이 1/2~1/3.

### D. Files API + 비디오 직접 참조 — 구조 변경 필요, 중장기
scene 별 trim 된 mp4 를 `client.files.upload(...)` 로 올리고 `Part.from_uri(uri, mime_type="video/mp4")` 로 참조. 이미지 N 장 대신 "video tokens(초당 fixed rate)" 로 과금되어 보통 더 저렴. 같은 파일을 foley/non-foley 가 공유 가능.

### E. 해상도 재확인
`scale=768:-2 → 512:-2` 로 낮춰보고 결과 품질·토큰 비교. tiled → non-tiled 로 떨어지면 장당 토큰이 유의미하게 감소.

### F. 재시도 예산 차별화
- 고단가 모델(`pro`): `LLM_MAX_RETRIES=2` 로 축소.
- 또는 503 이 반복되면 **fallback 모델(`flash-lite`)** 로 한 번 다운그레이드 재시도하는 패턴.

### G. 비용 원인을 metric 으로 분해
현재 `llm_usage.by_stage` 는 prompt/output/cached 토큰을 stage 단위로 집계한다. 여기에 **이미지 토큰만 따로** 분리(Gemini 응답의 `prompt_tokens_details.modality_breakdown` 등) 해서 Langfuse metadata 에 attach 하면, "어느 stage 의 이미지 비용이 튀는지" trace 비교로 즉시 보인다.

## 3. 적용 우선순위 요약

| 순서 | 항목 | 난이도 | 예상 절감 |
|---|---|---|---|
| 1 | A. scene frame 공유 | 중 | ~50% (foley/non-foley 이미지 토큰) |
| 2 | B. prompt caching | 중 | scene 수 비례, 10+ 부터 체감 |
| 3 | C. global frames ↓ | 하 | global 호출당 1/2~1/3 |
| 4 | G. image-token metric 분리 | 하 | 절감은 아니지만 후속 의사결정 재료 |
| 5 | D. Files API 경로 | 상 | 구조적 이득, 중장기 |
| 6 | E. 해상도 | 하 | 한계적, 품질 트레이드오프 |
| 7 | F. 재시도 예산 | 하 | 실패 빈도에 비례 |

## 4. 지금 당장 지키면 좋은 가드레일

- `tools=` 에 `google_search` / grounding 추가 **금지** (Search grounding 은 호출당 별도 과금).
- 실험 시에도 scene 수·fps·max_frames 를 기록하는 습관 (Langfuse trace metadata 에 반드시 포함되도록 §2.G 작업 함께 가면 좋음).
- PRICING 딕셔너리(`ai/llm_client.py`) 는 새 모델 쓸 때마다 즉시 업데이트. 안 그러면 cost 가 0 으로 찍혀 실제 비용 왜곡.
- `LLM_USAGE_LOG=logs/llm_usage.jsonl` 켜두고 JSONL 도 남겨두면, Langfuse 장애/삭제 시에도 사후 분석 가능.

## 5. 참고

- 현재 "background search" 경로는 사용 중이 아님 (안전).
- 현재 "base64 인라인 이미지" 경로는 사용 중 → §1.2, 개선안 A/B/D 가 여기에 해당.
- 관련 설정: `ai/config.py` (stage 별 모델), `ai/llm_client.py` (PRICING, 재시도 파라미터), `ai/analyze_local_foley.py` / `ai/analyze_local_non_foley.py` (scene 단위 호출 루프).
