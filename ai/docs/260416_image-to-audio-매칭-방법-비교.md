# 이미지 기반 오디오 매칭 방법 비교 분석

## 방법별 비교 분석

### 방법 1: Image → Image(DB) 유사도 검색 → 해당 이미지의 음악 제공

**개념**: 클릭한 프레임과 시각적으로 유사한 이미지를 DB에서 찾고, 그 이미지에 매핑되어 있던 오디오를 가져오는 방식.

**장점**:
- 직관적이고 설명 가능함 — "이 장면과 비슷한 장면에서 이 소리가 쓰였다"
- 이미 검증된 조합(이미지-오디오 페어)을 재활용하므로 품질이 보장됨
- 비전 임베딩(CLIP, Gemini embedding)은 성숙한 기술

**단점**:
- **Cold start 문제가 치명적**: `sound_assets` 테이블에 이미지가 매핑되어 있지 않음. 현재 ERD를 보면 sound_assets에는 오디오 파일과 텍스트 메타데이터만 존재하고, "이 소리가 어떤 장면에서 쓰였는가"라는 이미지-오디오 페어 데이터가 없음
- 페어 데이터를 축적하려면 별도의 수집/큐레이션 파이프라인이 필요 — 사용자가 편집한 프로젝트에서 역으로 수집하는 방식이 될 텐데, 초기에는 데이터가 0
- 이미지 임베딩 저장을 위한 추가 테이블/컬럼 필요
- "비슷하게 생긴 장면"이 "비슷한 소리가 필요한 장면"과 같지 않을 수 있음 (예: 밤의 도시 vs 낮의 도시 — 시각적으로 유사하지만 사운드스케이프가 다름)

**추천도**: ⭐⭐ (장기적으로 데이터가 쌓이면 보조 시그널로 유용하지만, 단독 방법으로는 부적합)

---

### 방법 2: Image → Audio(DB) 크로스모달 유사도 검색

**개념**: 이미지와 오디오를 같은 임베딩 공간에 매핑하여, 이미지 임베딩으로 직접 오디오를 검색하는 방식.

**장점**:
- 중간 단계 없이 직접 매칭 — 파이프라인이 단순
- 텍스트 변환 시 손실되는 시각적 뉘앙스를 보존 가능

**단점**:
- **크로스모달 임베딩이 현실적으로 매우 어려움**: Image-Audio 크로스모달 모델(ImageBind 등)은 존재하지만, 현재 프로젝트의 오디오 도메인(Foley, SFX, Ambience 등 세분화된 사운드 이펙트)에 대해서는 정밀도가 낮음
- 현재 DB의 `sound_assets.embedding`은 `vector(3072)` — Gemini 텍스트 임베딩 기반으로 설계됨. 크로스모달 모델을 쓰려면 임베딩을 전부 재생성해야 함
- ImageBind 같은 모델은 "개가 짖는 장면 → 개 짖는 소리" 수준은 되지만, "비 오는 창문 장면 → 빗소리 + 유리 진동 + 실내 반향"처럼 레이어드된 사운드 디자인에는 부족
- 모델 호스팅/추론 비용이 추가됨
- Foley 사운드는 매우 구체적인 카테고리 매칭이 필요한데(예: 나무 바닥 발자국 vs 콘크리트 발자국), 크로스모달 임베딩은 이 수준의 세밀함을 제공하기 어려움

**추천도**: ⭐⭐ (기술적으로 흥미롭지만 현재 인프라와 호환성이 낮고, Foley 도메인에서 정밀도 부족)

---

### 방법 3: Image → Text(API) → Audio(DB) — 추천

**개념**: 이미지를 Gemini 비전 API로 분석하여 텍스트 디스크립션(category_path, tags, description)을 생성하고, 이 텍스트의 임베딩으로 DB의 오디오를 검색.

**장점**:
- **현재 아키텍처와 완벽히 정렬**: 이미 파이프라인이 정확히 이 패턴으로 동작 중. `analyze_local_foley.py`가 프레임 → Gemini → (category_path, tags, description) 생성, 백엔드가 텍스트 임베딩 → pgvector 검색 담당
- **`sound_assets.embedding`이 이미 `vector(3072)` Gemini 텍스트 임베딩으로 설계되어 있음** — 추가 인프라 변경 없이 동일한 검색 파이프라인 재사용
- **텍스트가 "번역 레이어" 역할**: Gemini 비전은 "나무 바닥 위를 걷는 캐릭터"를 `["Foley", "Footsteps", "Wood"]` + `tags: ["indoor", "slow", "barefoot"]`로 정밀하게 변환 가능 — taxonomy.json의 카테고리 체계와 직접 연동
- **해석 가능성**: 중간 텍스트가 생성되므로 디버깅/품질 개선이 용이. 왜 특정 오디오가 매칭되었는지 사용자에게 설명 가능
- **하이브리드 검색 가능**: 텍스트 임베딩 유사도 + category_path 필터링 + tags 매칭을 결합하면 정밀도 대폭 향상 (예: `WHERE major_id = 'Foley' AND mid_id = 'Footsteps'` + 임베딩 유사도 순위)
- Gemini API 호출 비용은 이미 파이프라인에서 발생 중이므로 추가 비용 미미

**단점**:
- API 호출 레이턴시 (실시간 클릭 시 ~1-3초 대기)
- 텍스트 변환 시 일부 시각적 뉘앙스 손실 가능 (하지만 Gemini의 비전 능력이 충분히 강력)
- API 의존성 — 오프라인 동작 불가

**추천도**: ⭐⭐⭐⭐⭐

**추천 이유 요약**: 현재 `pipeline.py`의 Stage 2(foley 분석)가 이미 정확히 이 패턴을 사용하고 있고, `sound_assets.embedding(vector(3072))`과 taxonomy 기반 카테고리 체계가 이 방식에 맞춰 설계되어 있음. 새로운 인프라 없이 기존 코드를 거의 재사용할 수 있음.

## 추가 방법 인사이트

### 방법 4: Image → Text(API) → Text Embedding + Category Filtering (하이브리드)

방법 3의 강화 버전. 단순 벡터 유사도만 쓰지 않고:

```
1. Gemini 비전 → category_path + tags + description 생성
2. category_path로 후보군 사전 필터링 (SQL WHERE)
3. description 임베딩으로 필터링된 후보 내에서 순위 매기기
4. tags 매칭으로 추가 가중치
```

이렇게 하면 "발자국 소리가 필요한데 빗소리가 매칭되는" 문제를 구조적으로 방지함. 현재 taxonomy.json의 3단계 카테고리 체계가 이 필터링에 바로 활용 가능.

### 방법 5: 캐시 기반 사전 분석

사용자가 비디오를 업로드하면 파이프라인이 이미 전체 프레임을 분석함. 이 분석 결과(`AiEvent`)를 타임라인에 매핑해두면, 클릭 시 API 호출 없이 해당 타임스탬프의 사전 분석 결과를 즉시 반환 가능.

```
업로드 시: Video → pipeline.py → AiEvent[] (이미 수행 중)
클릭 시: timestamp → 해당 구간의 AiEvent 조회 → pgvector 검색 (API 호출 불필요)
```

이 방식은 **실시간 응답이 가능하고**, 이미 구현된 파이프라인 결과를 재활용하므로 가장 실용적.

### 방법 6: 멀티모달 Re-ranking

방법 3이나 4로 Top-K 후보를 뽑은 뒤, 원본 이미지 + 후보 오디오의 텍스트 설명을 함께 Gemini에 넣어 "이 장면에 가장 적합한 소리 3개를 골라줘"라고 re-ranking하는 방식. 정밀도가 높지만 비용과 레이턴시가 증가.

---

## 최종 추천

**즉시 구현**: 방법 5 (사전 분석 캐시) + 방법 4 (하이브리드 검색)

현재 파이프라인이 이미 비디오 전체를 분석하여 `AiEvent[]`를 생성하므로, 클릭 시점에는 API 호출 없이 해당 타임스탬프의 분석 결과로 pgvector 검색만 수행하면 됨. 이것이 레이턴시, 비용, 정밀도 모든 면에서 최적.
